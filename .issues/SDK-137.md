## Why

KMS context (`contextId` + `epochId`) rotates on the server. A permit signed under context N is rejected once the server moves to context N+1. Today this surfaces as an opaque decrypt failure — the SDK has no notion that the permission has gone stale, so the user has no path forward except a manual `revokePermits()` followed by a fresh `allow()`, often blind to the cause.

Architecturally, a permission is conditionally valid: signature + validity window + current KMS context. The model already encodes the first two; the third is implicit and must become explicit on the failure path.

## What

When `userDecrypt` (or `userDecryptAs`) fails because the underlying permission's KMS context is stale, the SDK invalidates that permission, re-runs the `allow` planning step, prompts once, and retries.

### Architectural constraints

- **Detection is at the relayer/error boundary, not inside** `CredentialService`. The service trusts the store; the orchestrator (`ZamaSDK.userDecrypt`) sees the error and triggers recovery.
- **Recovery is bounded.** One retry. Two stale-context failures in a row -> throw. The SDK never silently loops on wallet prompts.
- **Recovery is per-permission, not per-scope.** Other permissions in the same scope remain valid until they too fail.
- **No public API changes.** Consumers see at most one extra wallet prompt followed by a successful result.

## How

```
userDecrypt(handles):
  result = credentialService.allow(contracts)
  for each (contract, handles) group:
    permission = pick(result, contract)
    try:
      relayer.userDecrypt({ permission, ... })
    catch StaleContextError:
      permissionStore.invalidate(permission)         // drop just this record
      result     = credentialService.allow([contract])  // re-plan; one wallet prompt
      permission = pick(result, contract)
      relayer.userDecrypt({ permission, ... })       // retry once; throw on second failure
```

### Assumption

The relayer surfaces stale-KMS-context failures as a **distinguishable error type** (or error code). If the relayer does not differentiate stale-context errors from other decrypt failures, the detection heuristic must be documented and tested in isolation. See also the [epic](SDK-89.md) §Assumptions & Dependencies.

## Done When

- [ ] Stale-context error on `userDecrypt` → the stale permission is removed from the store → `allow` re-plans and prompts once → retry succeeds.
- [ ] Two consecutive stale-context errors for the same contract → the second failure bubbles up to the caller (no infinite retry loop).
- [ ] Stale permission for contract A does not affect permissions for contracts B, C in the same scope.
- [ ] `userDecryptAs` (delegated path) follows the same recovery logic.
- [ ] No public API changes — consumers see at most one extra wallet prompt, then a successful result or a thrown error.
