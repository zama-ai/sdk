## Why

The foundation ([SDK-134](SDK-134.md)) ships credentials persisted in plaintext via `GenericStorage`, with security delegated to the storage backend. This is correct for most contexts: browser dApps have IndexedDB behind OS-level disk encryption, mobile apps have platform keychains, server operators have KMS/Vault/HSM.

The gap is **headless contexts** — CLI tools, agentic operators on bare metal, local dev environments — where no platform keystore exists and no operator KMS is available. The consumer has no inherently secure storage backend to delegate to. Asking them to implement a custom encrypting `GenericStorage` adapter is possible but high-friction.

The old system "solved" this with PBKDF2 derivation from the permit signature, but the signature was stored alongside the encrypted data — lock and key in the same drawer. This also broke for MPC/custodian wallets that don't produce deterministic signatures across ceremonies.

## What

An optional `derivationSecret` config that, when provided, wraps the ML-KEM private key before writing to storage and unwraps on read. The secret comes from the consumer's environment (env var from secrets manager, mounted file, KMS-unwrapped blob) — the SDK never manages or stores it.

### Mechanism

```
wrappingKey = HKDF-SHA256(
  ikm: derivationSecret,
  salt: walletAddress,
  info: "zama-sdk-keypair-wrapping-v1"
) -> 32 bytes

encrypt: AES-256-GCM(wrappingKey, random IV, plaintext privateKey) -> ciphertext
decrypt: AES-256-GCM(wrappingKey, IV, ciphertext) -> plaintext privateKey
```

Same wallet + same secret deterministically produces the same wrapping key. The keypair itself is still generated randomly (no seeded keygen dependency on the relayer WASM).

### Properties

- **Does not eliminate storage** — keypairs are still persisted. It eliminates the requirement for **secure** storage.
- **No signature determinism dependency** — the secret is external, not derived from wallet signatures.
- **Consumer controls secret lifecycle** — rotation invalidates persisted keypairs (next `allow()` generates fresh). Not catastrophic, just a re-prompt.
- **Additive** — the `KeypairVault`, `PermissionStore`, and `CredentialService` interfaces are unchanged. Wrapping is applied transparently at the storage write/read boundary inside the vault.

### Locked config surface

```ts
interface ZamaSDKConfig {
  permitDuration?: number;
  storage?: GenericStorage;
  derivationSecret?: string | Uint8Array; // new, optional
}
```

### Storage modes after this ticket

| Mode                               | Config                         | Storage needed? | Secure storage?                 |
| ---------------------------------- | ------------------------------ | --------------- | ------------------------------- |
| **Persistent, delegated security** | `storage` provided (default)   | Yes             | Yes (consumer's responsibility) |
| **Persistent, wrapped**            | `storage` + `derivationSecret` | Yes             | No (any KV store)               |

## How

1. Add `derivationSecret` to `ZamaSDKConfig` and thread it into `CredentialService` -> `KeypairVault`.
2. In `KeypairVault`: if `derivationSecret` is present, wrap the private key with `HKDF(secret, address) -> AES-256-GCM` before calling `storage.set()`, and unwrap after `storage.get()`.
3. Permissions are **not** wrapped — they contain only EIP-712 signatures (public data) and contract addresses.
4. Handle rotation: if `storage.get()` returns data that fails to decrypt (wrong secret), treat it as a cache miss — delete stale entry, generate fresh keypair, persist wrapped.
5. Tests (see Done When below).

## Done When

- [ ] `KeypairVault` wraps the private key with `HKDF(derivationSecret, walletAddress) → AES-256-GCM` before writing to storage when `derivationSecret` is configured.
- [ ] `KeypairVault` unwraps the private key on read when `derivationSecret` is configured.
- [ ] Round-trip: wrap → persist → read → unwrap produces the original private key.
- [ ] Secret rotation: changing `derivationSecret` invalidates old keypair — vault treats decrypt failure as a cache miss, deletes the stale entry, generates a fresh keypair, and persists it wrapped with the new secret.
- [ ] Wrong secret: same behavior as rotation — regeneration, not a crash.
- [ ] No wrapping when `derivationSecret` is absent — regression guard confirming plaintext persistence is unchanged.
- [ ] Permissions are never wrapped (only the private key is).
- [ ] `ZamaSDKConfig.derivationSecret` accepts `string | Uint8Array` and is threaded through to `KeypairVault`.

### Out of scope

- Seeded keypair derivation (storage-free mode). Requires relayer WASM to expose `ml_kem_pke_keygen_from_seed()`. Tracked separately if/when the relayer ships it.
- Permission wrapping — permits are public data, wrapping them adds complexity without security benefit.
