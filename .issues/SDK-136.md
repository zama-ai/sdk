## Why

Without widening, every new contract a user touches accumulates a fresh permit. A user growing their dApp footprint pays one wallet prompt per new contract, indefinitely, even though the protocol allows up to 10 contracts per permit. This contradicts the principle the 10-contract cap exists to enable: minimum number of wallet prompts for a given coverage.

The model already supports widening — a permission is a `(signedContractAddresses, signature, validity)` tuple, and re-signing replaces it atomically. The foundation sub-issue deliberately deferred this so the rewrite stayed minimal.

## What

When `allow()` resolves the uncovered set, prefer widening an existing permission to creating a new one — provided the union stays within the 10-contract cap. **No public API changes**: this is a planning improvement inside `CredentialService.allow`.

### Architectural constraints

- **Widening replaces, never extends in place.** The new permission has a fresh `startTimestamp` and a fresh signature. The old record is dropped only after the new one is stored.
- **The 10-contract cap is a hard invariant.** A permission's `signedContractAddresses` is never grown past 10. If no candidate fits, fall back to creating new permissions (chunked by 10 as in the foundation).
- **Wallet rejection leaves state untouched.** Mid-flight cancellation of widening must not corrupt or delete the existing permission.
- **Selection is deterministic.** Pick the candidate by a stable rule (e.g., largest existing overlap with `uncovered`, ties broken by most-recent `startTimestamp`).

## How

```
allow(contracts, delegator?):
  uncovered = contracts \ covered
  if uncovered empty: return existing
  candidate = pick existing permission where |signed U uncovered| <= 10
  if candidate:
    new_set    = sort(union(candidate.signed, uncovered))
    new_signed = sign(new_set)            // wallet prompt
    replace(candidate, Permission { signed: new_set, permit: new_signed,
                                    startTimestamp: now, durationDays })
  else:
    chunk uncovered by 10, sign each, store individually   // unchanged from foundation
```

## Done When

- [ ] Widen happy path: existing `[A,B]`, request `[A,B,C]` → one wallet prompt, one permission with `[A,B,C]`. Old `[A,B]` permission is replaced.
- [ ] Widen exceeds cap: existing `[A..J]` (10), request `[K]` → new permission for `[K]` (falls back to foundation chunking).
- [ ] Multiple candidates: the candidate with the largest overlap with `uncovered` is selected; ties broken by most-recent `startTimestamp`. Behavior is deterministic.
- [ ] Wallet rejection during widen: original `[A,B]` permission survives untouched in the store.
- [ ] No public API changes — `allow()` signature and return type are unchanged.
- [ ] Widened permission gets a fresh `startTimestamp` and `durationDays` (not inherited from the old one).
