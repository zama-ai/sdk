## Why

The current credentials system fuses three orthogonal concerns into one `(signer, chainId)` blob: an identity-scoped ML-KEM keypair, a chain-scoped permit, and the AES entropy that protects the keypair at rest. These are independent in the protocol — one keypair per signer (chain-independent), many permits per (signer, chain), each binding a contract subset, each with its own validity window. Folding them together produces three structural failures (see [epic](SDK-89.md) §2): no way to express more than 10 authorized contracts, keypair orphaning when the permit is revoked, and a parallel `DelegatedCredentialsManager` kept in sync by hand. No incremental patch fixes this — the model is wrong, the code follows from the model.

The old PBKDF2-from-permit-signature at-rest "encryption" stored the key material (session signature) alongside the encrypted data — lock and key in the same drawer. The replacement is not better SDK-layer encryption but delegated security: the consumer provides a storage backend with the security properties they need.

## What

Replace the entire credential internals with the correct shape: an identity-scoped keypair vault, a chain-scoped 1-to-many permission store, and a single coordinating service. This is an atomic swap — the old machinery is deleted, the new one takes its place. From a consumer's perspective the result is functional parity (same operations, same observable behavior) plus persistent credentials that survive page reloads.

### Invariants (must NOT change)

These existing behaviors must survive the refactor unchanged. Any test that validates them today must still pass.

- `userDecrypt` returns the same decrypted values for the same handles — the refactor does not change what the KMS returns or how shares are combined.
- `Token.allow()`, `Token.revoke()`, `Token.isAllowed()` continue to work as thin wrappers around `sdk.*` methods.
- React hooks (`useAllowance`, `useDecrypt`, etc.) are unaffected — they call through the SDK's public surface, which is unchanged.
- The `DecryptCache` is independent — credential changes do not invalidate or corrupt cached decrypted values.
- `GenericStorage` contract is unchanged — no new methods, no changed semantics.

**Done when:**

- [ ] `allow([A, B, C])` prompts for a permit covering `[A, B, C]` when no coverage exists; does not prompt when coverage already exists.
- [ ] `allow` with >10 contracts chunks into multiple permits and stores each individually.
- [ ] Partial `allow` success: user approves first permit, rejects second — first permit is persisted. Next `allow` only re-prompts for uncovered contracts.
- [ ] `allowAs(delegator, contracts)` follows the same path as `allow` with `delegatorAddress` set to the delegator.
- [ ] `isAllowed` returns `true`/`false` based on stored permissions — no side effects, no wallet prompt, no keypair generation.
- [ ] `revokePermits()` wipes all permissions for `(signer, chainId)`; keypair survives; next `isAllowed` returns `false`.
- [ ] `revokePermits([A])` removes only contract `A` from the relevant permission(s); other contracts remain covered.
- [ ] `clearCredentials()` wipes the keypair and cascades to all permissions across all chains.
- [ ] Signer change triggers cascade-clear for the previous signer and eager keypair generation for the new signer.
- [ ] Chain change is a no-op — keypair survives, permissions for the new chain are loaded.
- [ ] Credentials persist across page reloads — no re-prompt after refresh when valid permits exist in storage.
- [ ] `DelegatedCredentialsManager`, `CredentialsManager`, `BaseCredentialsManager`, `credential-crypto.ts`, `credential-validation.ts`, `session-signatures.ts`, and `types/credentials.ts` are deleted.

## How

This refactor touches three layers: the credential internals (new), the `ZamaSDK` class (rewired), and `Token`/`ReadonlyToken` (simplified).

### Locked public surface

These are the contracts that consumers depend on. They are fixed — the implementer does not change signatures, semantics, or naming.

**`ZamaSDK` methods:**

```ts
allow(contracts: Address[]): Promise<void>
allowAs(delegator: Address, contracts: Address[]): Promise<void>
isAllowed(contracts: Address[]): Promise<boolean>           // pure — no side effects, no wallet prompt
isAllowedAs(delegator: Address, contracts: Address[]): Promise<boolean>
userDecrypt(handles: DecryptHandle[]): Promise<Record<Handle, ClearValueType>>
revokePermits(contracts?: Address[]): Promise<void>          // no arg = wipe all for (signer, chain)
clearCredentials(): Promise<void>
```

**`ZamaSDKConfig` (credential-related fields only):**

```ts
interface ZamaSDKConfig {
  keypairTTL?: number;
  storage?: GenericStorage; // backing store for credentials + DecryptCache
  permitDuration?: number; // days, default 30, maximum = keypairTTL
  permitStorage?: GenericStorage; // backing store for permits
}
```

The permit duration lifetime is implicitly bound by its keypair.

**`Token` / `ReadonlyToken`:**

```ts
revoke(): Promise<void>        // delegates to sdk.revokePermits([this.address])
isAllowed(): Promise<boolean>  // delegates to sdk.isAllowed([this.address])
```

### Locked internal interfaces

Downstream sub-issues ([SDK-136](SDK-136.md), [SDK-137](SDK-137.md)) depend on these interfaces. They are fixed for this ticket and must not be changed without updating the downstream issues.

```ts
interface KeypairGenerator {
  generateKeypair(): Promise<{ publicKey: Hex; privateKey: Hex }>;
}

interface PermitFactory {
  createEIP712(
    publicKey: Hex,
    contracts: Address[],
    startTimestamp: number,
    durationDays: number,
  ): Promise<EIP712TypedData>;
  createDelegatedUserDecryptEIP712(
    publicKey: Hex,
    contracts: Address[],
    delegator: Address,
    startTimestamp: number,
    durationDays: number,
  ): Promise<EIP712TypedData>;
}

interface PermitSigner {
  signTypedData(td: EIP712TypedData): Promise<Hex>;
  getAddress(): Promise<Address>;
  getChainId(): Promise<number>;
}
```

```ts
class CredentialService {
  constructor(cfg: {
    keypairGenerator: KeypairGenerator;
    permitFactory: PermitFactory;
    permitSigner: PermitSigner;
    keypairTTL?: number;
    permitDuration?: number;
    permitStorage?: GenericStorage;
    storage: GenericStorage;
  });
  initialize(): Promise<void>;
  allow(contracts: Address[], delegator?: Address): Promise<AllowResult>;
  isAllowed(contracts: Address[], delegator?: Address): Promise<boolean>;
  revokePermits(contracts?: Address[]): Promise<void>;
  clearCredentials(): Promise<void>;
  handleIdentityChange(prev?: SignerIdentity, next?: SignerIdentity): Promise<void>;
}
```

### Architectural constraints

- **Three components, one facade.** `KeypairVault` (identity-scoped, chain-independent), `PermissionStore` (1-to-many permits per `(signer, chainId, keypairPublicKey, delegatorAddress)`), `CredentialService` (the only credentials object `ZamaSDK` holds).
- **Delegation is an axis, not a fork.** Same vault, same store, same code paths. `delegatorAddress` is a field on the permission scope; for direct decrypts it equals `signerAddress`.
- **Composition root is `ZamaSDK`.** The service depends only on the three injected interfaces above — never on the relayer or signer adapter directly.
- **`isAllowed` is pure.** A store lookup. No keypair generation, no awaitable side effects on credential state, no wallet prompt. Returns `false` when no keypair exists yet.
- **`ZamaSDK` owns identity events.** The service does not subscribe to anything; it receives `handleIdentityChange(prev, next)` calls from `ZamaSDK`.
- **Delegated security — no SDK-layer encryption.** The private key is stored in plaintext in the backing storage. Optional `derivationSecret` wrapping is a separate sub-issue ([SDK-135](SDK-135.md)).

### Behavioral contracts

**`allow(contracts, delegator?)`:**

```
resolve (signerAddress, chainId, keypair, delegatorAddress)
list existing permissions for scope, prune expired
if union of existing permissions covers all requested contracts:
  return without prompting
else:
  uncovered = requested \ covered
  chunk uncovered into groups of ≤ 10
  for each chunk:
    sign a new permit via PermitSigner     // wallet prompt
    store the permission individually       // partial success survives mid-flight rejection
  return keypair + all matching permissions
```

**`revokePermits()` (no arg):** Wipe all permissions for `(signer, chainId)`. Keypair survives.

**`revokePermits(contracts)`:** For each permission in scope, remove the specified addresses from `signedContractAddresses`. Drop permissions whose address set becomes empty. Keypair survives.

**`clearCredentials()`:** Wipe the keypair for the current signer. Cascade-delete every permission across all chains that references that keypair's public key.

**`handleIdentityChange(prev, next)`:** Signer address changed -> cascade-clear for prev, eager keypair generation for next. Chain-only change -> no-op.

### Verification

Unit tests for each component in isolation (vault, store, service), plus an integration test that exercises the full lifecycle: signer present -> `allow` prompts -> `userDecrypt` succeeds -> reload preserves credentials -> `revokePermits([token])` removes only that token -> `isAllowed` reflects the change. Mirror for the delegated flow.

The old credential files are deleted in the same PR — no deprecation period, no parallel existence.
